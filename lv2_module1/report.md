## 문제 1. 목표 입력과 응답 확인

### 설정

| 항목 | 값 |
|---|---|
| 모터 모델 | XM430-W350 (모델 1020) |
| 모터 ID | 12 |
| 통신속도 / 프로토콜 | 1 Mbps, Protocol 2.0 |
| 예제이름 | `opencr_position_p.ino` (제공된 예제, 수정 안함) |
| Kp | 1 (실측, `s 1 30 20`) |
| 목표각 | 20 deg (실측) |
| 속도상한 | 30 deg/s (실측) |
| 라즈베리파이 호스트명/포트/아키텍처 | pak / /dev/ttyACM0 / aarch64 (실측, [results/환경확인.txt](results/환경확인.txt)) |

### 업로드 확인

[results/upload.log](results/upload.log) 보면 `CRC OK 9B55F6 9B55F6 0.003000 sec` 다음에 `[OK] Download` 찍힘. 업로드는 이걸로 성공한거 맞고, 그 다음에 시리얼모니터 켜서 `s 1 50 90` 쳐봤더니 바로 `START: current position = 0 deg.`, `P SET Kp=1.0000...` 이렇게 응답 옴. 그래서 장치도 정상적으로 준비된 상태였다고 봄. (`READY:` 배너는 로그 켜기 전에 이미 지나가서 파일엔 안 남음. 그냥 그 부분은 못 잡은거)

### 실행 A 기록: 목표 변경(`s 1 30 20`) 이후 측정값

단위: target_deg=목표각[deg], position_deg=측정각[deg], error_deg=오차[deg], u_deg_s=제어출력(목표 각속도)[deg/s].

실측 로그(`results/실행A.log`)에서 뽑은 값:

| t_s | target_deg | position_deg | error_deg | u_deg_s |
|---|---|---|---|---|
| 2.000 | 20.000 | 0.000 | 20.000 | 20.610 |
| 2.500 | 20.000 | 6.064 | 13.936 | 13.740 |
| 3.000 | 20.000 | 11.689 | 8.311 | 8.244 |
| 4.001 | 20.000 | 17.139 | 2.861 | 2.748 |
| 5.001 | 20.000 | 18.984 | 1.016 | 1.374 |
| 8.601 | 20.000 | 19.336 | 0.664 | 0.000 |

t=8.601s 직후 `x` 입력 → `STOP: user` 응답까지 확인함(로그 마지막 줄).

전체 원본로그: [results/실행A.log](results/실행A.log)

### 관찰 설명

목표각 20deg로 바꾸자마자(t=2.000s) 오차가 20deg였고 Kp=1이니까 출력(u_deg_s)도 비슷하게 20.610deg/s로 나감. 그 다음부턴 오차 줄어드는 만큼 출력도 같이 줄어드는 게 로그에 그대로 보임. t=8.6초쯤 되니까 위치가 19.336deg에서 더 이상 안 올라가고 계속 그대로였음. 화면 보면서 한참 기다렸는데도 그대로라 `x` 눌렀고, `STOP: user` 뜨는거 확인하고 끝냄. 20deg에 정확히는 안 붙었고 0.664deg 정도 덜 갔는데, 어쨌든 로그랑 실제로 본 거랑은 똑같음.

## 문제 2. 오차와 피드백 해석

문제1이랑 같은 실행A 로그(`s 1 30 20`, Kp=1)를 오차·피드백 관점으로 다시 정리함.

### 사용 센서값

| 항목 | 출처 | 단위 |
|---|---|---|
| position_deg | 모터 안의 위치센서 값(PRESENT_POSITION)을 각도로 바꾼 값 | deg |
| speed_deg_s | 모터 안의 속도센서 값(PRESENT_VELOCITY)을 바꾼 값 | deg/s |
| error_deg | target_deg - position_deg (목표에서 지금 위치 뺀 값) | deg |
| u_deg_s | 계산해서 모터한테 실제로 보내는 속도 명령값 | deg/s |

### 오차 변화와 P 제어 출력의 관계 (실행A 실측)

| t_s | error_deg | p_deg_s (=Kp×error) | u_deg_s (실제로 모터한테 나간 값) | 비고 |
|---|---|---|---|---|
| 2.000 | 20.000 | 20.000 | 20.610 | 목표 막 바뀐 직후, 오차 최대 |
| 3.000 | 8.311 | 8.311 | 8.244 | 오차 줄어드는중 |
| 4.001 | 2.861 | 2.861 | 2.748 | |
| 5.001 | 1.016 | 1.016 | 1.374 | |
| 8.601 | 0.664 | 0.664 | 0.000 | 여기서 멈춰있길래 x로 정지 |

### 해석

`p_deg_s` 값이 `error_deg × Kp(=1)`랑 똑같이 나옴. 오차 줄어드는 만큼 출력도 같이 줄어듬. `u_deg_s`는 `p_deg_s`랑 완전히 똑같진 않고 조금씩 다름(예: error 1.016일때 u는 1.374). 오차가 0.664deg일 때 `u_deg_s`가 0으로 나오고, 그 뒤로는 위치가 19.336deg에서 안 바뀌고 그대로였음.

## 문제 3. P 게인 변경에 따른 응답 비교

Kp만 1 → 2로 바꿔서(목표각·속도상한은 동일) 한번 더 실행함(실행B, `s 2 30 20`).

### 비교 설정

| 항목 | 실행 A | 실행 B |
|---|---|---|
| Kp | 1 (실측) | 2 (실측) |
| 목표각 | 20 deg (동일) | 20 deg (동일) |
| 속도상한 | 30 deg/s (동일) | 30 deg/s (동일) |
| 로그 | [results/실행A.log](results/실행A.log) | [results/실행B.log](results/실행B.log) |

### 응답 비교 (실측)

| 항목 | 실행 A (Kp 1) | 실행 B (Kp 2) |
|---|---|---|
| 목표변경 직후 오차 | 20.000 deg (t=2.000s) | 20.000 deg (t=2.000s) |
| 초기 제어출력 p_deg_s(=Kp×error) | 20.000 deg/s (상한 안 걸림) | 40.000 deg/s → 속도상한(30) 넘어서 28.854 deg/s로 깎여서 나감 |
| t=3.000s 위치 | 11.689 deg | 16.260 deg (더 빨리 붙음) |
| 수렴(정지) 위치·오차 | 19.336 deg (오차 0.664deg), t≈5.5s부터 고정 | 19.688 deg (오차 0.312deg), t≈4.0s부터 고정 |
| 정지(STOP) 로그 | `x` → `STOP: user` 확인 (t≈8.6s) | `x` → `STOP: user` 확인 (t≈6.2s) |

### 해석

Kp=2에서는 초기 출력(40deg/s)이 속도상한(30deg/s)을 넘어서 28.854deg/s로 깎여서 나감. Kp=1은 이 제한에 안 걸림. t=3초 기준 위치는 Kp=2가 16.260deg, Kp=1이 11.689deg로 Kp=2가 더 빨리 감. 멈춘 위치도 다름. Kp=1은 오차 0.664deg, Kp=2는 오차 0.312deg에서 멈춤. Kp 높이니까 더 빨리 가고, 마지막에 남는 오차도 더 작았음.

## 문제 4. 제어와 통신의 역할 해석

이건 새로 뭘 실행한 건 아니고 제공된 예제 코드(`opencr_position_p.ino`) 읽고 통신 방식 정리한거임. 하드웨어 다시 돌릴 필요는 없었음.

### 제어 주기

코드 보면 대충 10ms에 한번씩(1초에 100번 정도) 반복해서 도는 걸로 되어있음. 한 번 도는데 너무 오래 걸리면(50ms 넘어가면) 뭔가 문제 있다고 보고 멈춰버리게 해놨음. 화면에 찍히는 로그는 1초에 10번 정도만 나오는 거라, 로그 찍히는 속도랑 실제로 계산 도는 속도는 다름(계산은 로그보다 훨씬 자주 함). 한 번 돌 때마다 하는 일은: 지금 위치·속도를 모터한테 물어보고, 목표랑 얼마나 차이나는지 계산하고, 그 차이에 Kp 곱해서 얼마나 빠르게 움직일지 정하고, 그 값을 모터한테 보내는 순서임.

### 통신 흐름

OpenCR이랑 모터는 선 하나로 연결돼서 시리얼로 주고받음(1초에 백만번 정도 속도, ID 12번 모터랑 연결). 한 번 돌 때마다 위치 물어보고, 속도 물어보고, 이동 명령 보내고 이렇게 세 번 주고받는 구조임. 코드 주석 보면 지금은 모터 하나만 이렇게 순서대로 하나씩 물어보고 있고, 나중에 모터 여러개 쓰거나 더 빠르게 해야되면 다른 방식으로 바꿔야 한다고 적혀있음. 물어봤는데 10ms 안에 답이 안 오면 바로 에러로 보고 모터를 꺼버림(다시 켜려면 리셋해야됨).

명령어 입력받는 쪽(PC에서 s/k/x 같은거 치는 곳)은 완전히 다른 선으로 되어있어서, 모터랑 통신하는 거랑은 안 섞임.
